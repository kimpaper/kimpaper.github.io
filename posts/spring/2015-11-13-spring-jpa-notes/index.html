2015년 가을에 JPA 를 처음 붙여보면서 다섯 번에 나눠 올렸던 글을 한 페이지로 합쳤다. 따로 보면 토막글이라 순서대로 읽기가 불편했다.

그때 상황은 이랬다. 거의 다 mybatis 로 개발하고 있었는데 JPA 가 대세라길래 가벼운 프로젝트에 얹어봤다. 자료가 많아서 설정 자체는 어렵지 않았다. mybatis 를 한번에 다 걷어낼 자신은 없었고 기존 트랜잭션에 영향을 주지 않는 선에서 얹는게 목표였다.

import com.google.gson.annotations.Expose;
import com.google.gson.annotations.SerializedName;

import javax.persistence.*;

@Entity
@Table(name="tb_notice")
public class Notice {
    @Id
    @GeneratedValue(strategy = GenerationType.AUTO)
    @Column(name = "notice_id")
    @SerializedName(value = "notice_id")
    @Expose
    private Integer noticeId;

    @Column(name="title", nullable = false)
    @Expose
    private String title;

    @Column(name="content", nullable = false)
    @Expose
    private String content;

    @Column(name="reg_date", nullable = false)
    @SerializedName(value = "reg_date")
    @Expose
    private String regDate;

    @Column(name="del_yn", nullable = false)
    @Expose(serialize = false, deserialize = false)
    private String delYn;

    public Integer getNoticeId() {
        return noticeId;
    }

    public void setNoticeId(Integer noticeId) {
        this.noticeId = noticeId;
    }

    public String getTitle() {
        return title;
    }

    public void setTitle(String title) {
        this.title = title;
    }

    public String getContent() {
        return content;
    }

    public void setContent(String content) {
        this.content = content;
    }

    public String getRegDate() {
        return regDate;
    }

    public void setRegDate(String regDate) {
        this.regDate = regDate;
    }

    public String getDelYn() {
        return delYn;
    }

    public void setDelYn(String delYn) {
        this.delYn = delYn;
    }
}

설정은 여기까지가 끝이다. 문제는 실제로 쓸 때 요령이 필요하다는 것. 제대로 이해하지 않고 쓰면 성능에 영향을 준다고 한다.

연관관계 조회

테이블 관계가 이런 상황이다.

1

tb_member -< tb_member_inter >- tb_inter

원하는 조회 조건은 두 가지였다.

  • Member 를 가져오면 member 의 이미지들과 inter 목록을 함께 가져오도록
  • inter 의 상세 정보는 tb_inter 에 있으니 가져올 때 조인해서

하면서 걸렸던 것들.

  • MemberInter 의 PK 가 두 개라 클래스를 따로 만들어서 @IdClass 를 지정해야 한다
  • MemberInter 에서 제일 헷갈렸다. @ManyToOne 을 쓸 때 @JoinColumn 을 추가로 써야 한다
  • optional 을 true 로 하면 조인할 때 outer join 을 한다. false 는 inner join

FetchType 은 이렇게 갈린다.

  • FetchType.EAGER — 즉시 조회해서 데이터를 채운다
  • FetchType.LAZY — 필요할 때 DB 조회

필드명은 카멜케이스를 꼭 써야 한다. 안 그러면 나중에 method named query 에서 곤란해진다.

비슷한 속성으로 @Query 도 있다. 이건 Repository 에 쓴다.

둘의 차이가 중요하다.

  • named-query 는 코드 안에 선언한 Entity 를 기준으로 쿼리를 날린다
  • named-native-query 는 DB 에 직접 쿼리를 날린다. 그래서 result-class 를 지정해야 한다

NamedQuery 를 직접 호출하기

EntityManager 를 쓰면 orm.xml 에 정의한 NamedQuery 를 바로 실행할 수 있다.

repository 로 호출하면 getResultList 로만 실행되는 것 같다. update 로 반영된 row 수를 알아야 해서 아래처럼 했다.

정리

  • 설정은 라이브러리 두 개 + context-jpa.xml 하나면 끝난다
  • mybatis 와 같이 쓸거면 트랜잭션 매니저를 분리한다
  • 필드명은 카멜케이스로. 안 그러면 method named query 에서 막힌다
  • 복합키는 @IdClass 로 별도 클래스를 만든다
  • @ManyToOne 에는 @JoinColumn 을 같이 쓴다. optional 이 조인 종류를 가른다
  • 쿼리를 직접 써야 하면 orm.xml 의 named-query / named-native-query
  • update 의 반영 건수가 필요하면 EntityManager.createNamedQuery().executeUpdate()
